# hackiOS for Galaxy A8 (2018)

Experimental XNU bring-up project for the Samsung Galaxy A8 (2018), targeting the Korean **SM-A530N**.

## Status

Probe v2 ran on the Galaxy A8 and its live FDT reader reported three RAM banks: `0x80000000+0x3DA00000`, `0xC0000000+0x40000000`, and `0x880000000+0x80000000`. Probe v3 boot-looped; its struct copy pulled in a large Zig compiler runtime, growing the image from 15 KB to 146 KB. Probe v3.1 removes that copy and completed a live FDT parse on the phone, reporting 11 reserved ranges below 4 GiB. The high bank is still only a candidate XNU memory window until its addressability and ownership are checked.

The A530N bring-up has a successful clean Xcode kernel build in GitHub Actions: XNU 8796.141.3, 64-bit ARM, using the A5XELTE machine configuration with A8 overrides. Run [42771897514](https://github.com/ACTUALLYGUNBILEG/GALAXY-A8-2018-HACKIOS/actions/runs/42771897514) uploaded the `jackpotlte-xnu-kernel` artifact (73,587,821 bytes; seven-day retention), including the pthread-provider fix. V12 and the first v12-fbfix trial both reached a black screen with one bright pixel after the Samsung splash. Binary inspection found the v12 CI kernel did not contain the A8 early-console stage markers or framebuffer alias code: the workflow had omitted `apply_jackpotlte_bootstrap.py`, so the claimed framebuffer changes were only in the local source. The workflow now applies that patch before building. The earlier v11 Mach-O was a guarded one-instruction patch to the v10 linked kernel because Windows/WSL lacks Apple's Xcode linker and SDK. HakiOS's post-link symbol-set/export checker still reports donor `IOService` IORPC exports. The WSL-only diagnostic configuration disables donor `SWEET_HFS`; its integration expects macOS target headers, while that build uses the iPhoneOS 16.5 SDK.

Candidate v1 boot-looped at the Samsung logo; v2 reached XNU's five early markers through `arm_init_jump`; v3 reached `HANDOFF TO XNU`; v4 passed the splash but stopped at a black screen with one fixed bright pixel. V5 reached stage 7, then panicked because the framebuffer alias's L1 descriptor was not a table. V6 added that parent table and reached stage 20. V7 reached stage 33 at entry to `kernel_bootstrap`. V8 reached stage 42 in VM page-bucket setup. V9 progressed through stage 79 and then panicked while generating the platform UUID because the diagnostic kernel has no registered SHA-1 provider. V10 skipped that derived UUID and reached stage 82 before a CPU 0 startup timeout. V11 passed the CPU timeout, then panicked in BSD init because the pthread function table was null. V12 and the first v12-fbfix trial both stopped at the black screen with a single bright pixel after the Samsung splash. The v12-fbfix BOOT hash matched the installed image, but the kernel binary lacked the intended A8 console markers and framebuffer aliases because CI had not run the source patcher. The workflow now includes that source patch; later CI builds produced v16, which the user reports advanced to the Apple loading bar at letter n before stalling. None of these is an iOS install image: the handoff still assumes the bootloader supplies `linux,initrd-start/end` in the live FDT and that the provisional high-RAM window is safe. The Linux build compatibility shims disable usable UBSan/PGO diagnostics and C++ exit-time destructors for this target.

Latest device evidence: v16 includes the portable BearSSL AES CBC/ECB fallback. The user reports that its Apple loading bar reached the letter “n” and then stopped, with no panic visible. This is further visual progress than the prior AES-provider panic, but it does not identify which post-screen XNU call stopped; the v16 build has no checkpoints after stage 82 (`initialize_screen` returned). The next candidate adds stages 83–107 across commpage, policy/trust-cache, lockdown, BSD, and VM/pageout startup. [CI run 23](https://github.com/ACTUALLYGUNBILEG/GALAXY-A8-2018-HACKIOS/actions/runs/42844492937) produced the v16 kernel artifact. The loading bar remains kernel-side progress; no iOS userland has booted.

The user reports TWRP 3.7.1_12 remains available after candidate runs. Recovery identifies over ADB as product `twrp_jackpotlte`, device `jackpotlte`, model `Galaxy_A8_2018`. BOOT is `/dev/block/mmcblk0p12`, 32 MiB. The v12 installer ran through ADB sideload and TWRP logged a successful BOOT write plus matching readback hash. A read-only copy of the earlier BOOT contents is saved as `outputs/jackpotlte-current-boot-twrp.img` (SHA-256 `3FA84CA087577CD0BE001F38694BEDCA6412B3AA1964B2BAD172FF3CCEC45E17`). It is a checkpoint of the experimental partition, not a stock restore. The supplied `boot.img` has byte-identical ramdisk and DTBH data to this readback; its kernel differs because the readback contains a probe. This strongly ties the supplied base to the installed BOOT, although the exact firmware build identifier remains unknown.

The intended end goal is an experimental iOS 16.7.16 port using an iPhone X userland and an A8-specific XNU 8796 kernel, following the demonstrated S7/S8 ports. The SM-A530N is `jackpotlte` with an Exynos 7885. Live probes confirm EL1 entry, the A53 boot core, 4 KiB granule support, visible output using the Korean rev07 tree's `0xEC000000` framebuffer baseline, and three RAM banks. The v3.1 parse also captured the active reservation list. V11 reached BSD initialization; v12 reached loader handoff but still needs visible XNU progress. Stable kernel startup, GIC interrupt delivery, and 7885-specific XNU support remain unproven.

## Porting approach

Start with a tiny S-Boot handoff probe, then bring up XNU. The supplied `herolte` branch is a Galaxy S7 (SM-G930F / Exynos 8890) port built on the A5XELTE project; its stage-0 probe and Samsung image workflow are useful process references. The A8 is an Exynos 7885 device with a mixed Cortex-A53/Cortex-A73 CPU topology and eMMC storage, so donor memory maps, CPU startup, display drivers, and partition layouts must be re-derived.

The v16 trial cleared the earlier AES-provider panic and showed the Apple loading bar advancing to “n”, then stalling without a visible panic. The next milestone is a clean build with post-screen startup markers, followed by a BOOT-only diagnostic trial. The user confirmed a TWRP BOOT backup exists on removable storage; it restores the state it captured, not stock Android. The ADT describes one Cortex-A53, a provisional 512 MiB high-RAM window, the measured framebuffer, and Exynos 7885 GIC/timer candidates. The workflow runs on pushes to `main` and can also be started manually. No iOS userland or install image exists.
